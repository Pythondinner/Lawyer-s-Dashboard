# AI 隐私合规 Agent 重铸设计文档

面向岗位：AI 隐私合规。核心主张：这个工具不只是自动出合规结论，而是把"法律要求"和"工程实现"之间的翻译过程结构化、可留痕、可审计——在法务和工程师之间搭桥。

---

## 0. 融合还是分开？

**结论：共享前后端，中间两套独立法律引擎。**

```
┌─────────────────────────────────────────┐
│  阶段0：适用性判断（GDPR/AI Act 共用网关）  │
├─────────────────────────────────────────┤
│  阶段1：统一系统画像 intake（共用一份）     │
├──────────────────┬──────────────────────┤
│   GDPR 引擎        │   EU AI Act 引擎      │
│  （决策枢纽+目录）  │  （决策枢纽+目录）     │
├──────────────────┴──────────────────────┤
│  融合阶段：交叉引用报告（两法重叠点）        │
├─────────────────────────────────────────┤
│  双视图渲染：法务视图 / 工程视图            │
└─────────────────────────────────────────┘
```

- **不整体融合**：两部法律的决策枢纽结构完全不同（GDPR 是合法性基础+权利影响，AI Act 是风险分级+角色义务），各自条文独立演化（AI Act 有附件/授权立法更新更频繁），硬揉一套 prompt/schema 会降低每部法律判定的精确度——这正是第一版"法域混杂、缓解框架跨界"的根源。
- **不完全分开**：intake 重复采集会让用户体验变差，也做不了交叉引用（Art.27(4) AI Act ↔ Art.35 GDPR 这种法条自带的关联点），Harness 基础设施还要维护两份。

## 2. 阶段0：适用性判断（网关）

在采集任何细节之前先判断"这两部法律管不管得着你"：

| 判断项 | 对应条款 | 结果 |
|---|---|---|
| 系统输出/服务是否面向欧盟境内个人 | GDPR Art.3 / AI Act Art.2 域外效力 | 否→跳过对应引擎 |
| 是否处理个人数据 | GDPR 适用前提 | 否→跳过 GDPR 引擎 |
| 是否构成 Art.3(1) 定义下的"AI系统"，是否落入 Art.2 除外情形 | AI Act 适用前提 | 否→跳过 AI Act 引擎 |

## 3. 阶段1：统一系统画像 intake

按模块问，两个引擎共享同一份画像：

| 模块 | 字段（示例） | 主要喂给 |
|---|---|---|
| A. 主体与角色 | 系统名称、核心功能、价值链角色（提供者/部署者/进口商/分销商）、生命周期阶段 | 两个引擎 |
| B. 个人数据处理 | 数据类型、是否含 Art.9 敏感类别、数据主体（含是否儿童）、数据来源 | GDPR 主，AI Act 风险分级辅助 |
| C. AI 系统功能与自动化程度 | 用途场景（对照 Annex III 枚举，非自由文本）、**是否存在无实质人工介入且对个人产生法律/重大影响的自动化决策**（核心交叉字段） | AI Act 主，GDPR Art.22 辅助 |
| D. 数据流与地域 | 存储/处理地点、跨境传输机制 | 两个引擎 |
| E. 已有保障与文档 | 现有技术组织措施、现有文档（含"是否已做过 DPIA"——直接触发 Art.27(4) 复用逻辑） | 两个引擎 |

关键字段问法用工程师听得懂的话（"这个模型的输出会不会在没有人工复核的情况下直接触发一个业务动作？"），内部映射回法律要件——复用 `lawyer_shell.py` 现有的语义抽取机制，不用新建。

## 4. GDPR 引擎

### 4.1 决策枢纽（规则型为主，Art.6(f) 混合权衡型）

| 枢纽 | 要件 | 类型 | 结论生成方式 |
|---|---|---|---|
| Art.35(1)+WP248 DPIA 门槛 | 评分/画像、自动化决策法律效果、系统性监控、敏感数据、大规模、数据匹配、弱势群体、新技术、阻碍权利行使（9因素） | 规则型 | 命中≥2项→需做DPIA，代码判定 |
| Art.6/9 合法性基础 | 见此前案例三：五项规则初筛 + (f)正当利益三步权衡 | 混合 | 规则部分代码判定；权衡部分 LLM 论证+人工复核标注 |
| Art.22 自动化决策 | 见此前案例一：决定存在性、人工介入程度、影响重大性、例外事由、保障措施 | 规则型 | 代码 if/else 判定 |
| Ch.V 跨境传输机制 | 是否传出欧盟、目的地是否有充分性认定、有无 SCC/BCR | 规则型 | 代码判定 |
| Art.28 处理者关系/DPA | 是否使用第三方AI/云服务处理个人数据、该供应商是独立controller还是processor、是否已签订Art.28要求的处理协议条款 | 规则型 | 代码判定 |

### 4.2 目录型模块（复用现有 Harness 闭环，仅替换框架内容）
- `risk_identification.py`：风险分类换成 WP29/EDPB 语境下的真实类别（歧视、身份盗用、财务损失、去匿名化、丧失数据控制权等），并接入 `gdpr_articles.json` 做条文原文引用（现在没有，必须补）
- `necessity_justification.py`：结构基本保留，`reasoning` 字段直接复用给 Art.6(f) 权衡枢纽
- `mitigation_design.py`：**四层防御框架整体替换**为 Art.25（设计/默认隐私）+ Art.32（技术与组织措施）分类：技术措施（加密/假名化/访问控制/自动清除）、组织措施（DPA/DPO审核/培训/供应商条款）、治理措施（审计日志/事件响应/定期复审）

| 枢纽 | 要件 | 类型 | 结论生成方式 |
|---|---|---|---|
| Art.2/3 适用性 | 是否AI系统、是否除外情形 | 规则型 | 代码判定（阶段0已覆盖，此处复核） |

- `review_layer.py`：保留 schema 校验，可加一层"引用条款是否真实存在"的校验

## 6. 融合阶段：交叉引用报告

`fusion/cross_reference_map.py` 维护一张硬编码的法条勾连表，不是让模型自己联想：

| GDPR | AI Act | 关联性质 | 触发条件（来自 intake 字段） |
|---|---|---|---|
| Art.35 DPIA | Art.27 FRIA | **法条明文规定可合并进行**（Art.27(4)） | 已做过DPIA=是 且 高风险成立 |
| Art.22 自动化决策 | Art.14 人工监督 | 同一事实的两种法律后果 | C模块"自动化决策"字段=是 |
| Art.13/14 透明度 | Art.13/50 透明度 | 部分重叠，需求各有侧重 | 两法均适用时 |
| Art.9 敏感数据 | Annex III 生物特征分类 | 同一数据类型触发两法不同后果 | B模块敏感数据类别命中 |

融合报告只在命中这张表的行时才生成"交叉提示"，不做泛化联想——这也是这份报告可信度的来源。

## 7. 双视图输出（法务/工程之间搭桥）

同一条结论，渲染成两栏：

- **法务栏**：法条依据 + 人话解释 + 是"确定性结论（规则型）"还是"专业判断需复核（权衡型）"
- **工程栏**：具体改什么（字段/接口/UI流程）+ 验收标准写到能直接开工程票的颗粒度

`fusion/report_builder.py` 从同一份结构化 JSON 生成两种渲染，而不是维护两份内容。

`glossary/terms.json` 提供双向术语映射（法律术语→工程概念，工程概念→法律风险信号），报告渲染时按命中词自动插入解释脚注。

## 8. Observer 升级原则（贯穿两个引擎）

- **规则型枢纽**：Observer 检查"要件字段是否都有非空实质取值"，最终结论必须用代码从字段值机械推导并校验一致性，不依赖 LLM 二次判断
- **权衡型枢纽**：Observer 检查"论证是否有实质内容"（复用现有 `reasoning` 长度/覆盖率检查思路），结论必须标注"需人工复核"
- **目录型模块**：Observer 检查覆盖率+字段完整性（现有逻辑基本可沿用），可加"引用条款是否存在于 law_texts 语料"的校验，抓幻觉引用

## 11. 对话层设计：要件驱动的智能 intake

**问题**：旧版 `orchestrator` 按 `get_fields()` 固定顺序线性问一个个字段（`phase` 就是列表下标），`is_complete()` 只检查字段非空。用户一句话带出多个信息时，工具只认"当前 phase 对应的那一个"，其余浪费，还会接着按顺序追问已经答过的东西——这是"填空工具"感的直接来源。

**修复方向**：把驱动对话的数据结构从"固定字段列表+下标"换成"枢纽要件依赖图"，直接复用第4/5节已经定义好的枢纽表，法律推理和对话流程用同一套结构，不用维护两套逻辑。

### 11.1 状态表结构

每个枢纽维护一组要件，每个要件是一个 fact 对象：

```python
facts = {
  "processes_personal_data": {"value": None, "status": "unknown", "confidence": 0.0, "source_turn": None},
  "role": {"value": None, "status": "unknown", "confidence": 0.0, "source_turn": None},
  "automated_decision_exists": {"value": None, "status": "unknown", ...},
  ...  # 覆盖所有枢纽的所有要件
}
```

`status` 取值：`unknown`（未知）/ `known`（已抽取，代码可信）/ `inferred`（低置信度推断，需二次确认）。

### 11.2 每轮对话的处理逻辑

1. 拿用户这一句话，扫描**当前所有 `status=unknown` 的要件**（不是只看"当前phase"那一个），逐一尝试抽取——一句话可能同时命中好几个要件的 fact，全部更新
2. 抽取到的每个 fact 标记 `status`/`confidence`/`source_turn`（复现的时候能追溯是哪一句话、哪一轮产生的这个结论）
3. 重新计算哪些枢纽已经"要件齐全，可以出结论"（复用第8节 Observer 的判定逻辑，实时跑一遍）
4. 选择**下一个该问的要件**：优先级 = 能门控最多下游分支的要件 > 当前正在推进的枢纽里还缺的要件 > 其他。阶段0适用性判断的要件永远最优先（答"否"能直接砍掉整条分支，省掉后面一堆问题）
5. 命中的枢纽一旦"要件齐全"，立即触发对应的结论生成（代码判定或LLM论证），不用等到"整个表单填完"才统一处理——这样用户会感觉到工具在"边听边想"，而不是"问完才反应"

### 11.3 路由不再是单独的分类问题

旧版 `_route_tool`/`_detect_tool_trigger` 把"该走哪个工具"当成一次独立的意图分类任务来做，这正是语义抽取"不精准"感觉最强烈的地方（单次开放分类，信息量不够）。新设计里，**"该跑GDPR还是AI Act"直接是阶段0适用性判断的输出**，不再单独问："是否处理个人数据"这类阶段0要件本来就要采集，一旦采集到，两个引擎该不该跑就已经是代码能算出来的结论，不需要再单独做一次"意图路由"。

## 12. 语义抽取的精度原则

**核心结论：不是"语义提取 vs 硬编码"二选一，是分层——LLM 只负责"从自然语言里读出信息"，代码负责"从读出的信息里做判定/分支"。** 精度问题几乎总是出在"把判定这一步也交给LLM自由发挥"，而不是"用了语义理解"本身。

1. **凡是取值范围是闭集的字段，用结构化/枚举约束输出，不要自由文本+模糊匹配两段式。** 比如"角色"字段只有四个合法值，直接在 JSON schema 里用 `"enum": ["提供者","部署者","进口商","分销商"]` 约束模型输出，模型物理上不可能吐出集合以外的值；不合法就等于"未抽取到"，触发追问，而不是抽取到一个模糊字符串之后再靠代码去猜"这大概是哪个选项"。旧版 `_sanitize_field_value` 做的"抽取自由文本→再模糊匹配枚举"这个两段式设计，精度损耗恰恰发生在两段之间。

2. **工具路由收编进阶段0事实抽取（见11.3），不再是独立分类任务**——这是解决"语义路由不精准"最直接的办法：不是让分类更准，而是不再需要单独做这次分类。

3. **embedding+LLM 模糊判断层只保留给真正"低风险的模糊问题"**——判断用户这句话是不是在闲聊、要不要接一句工具触发提示，这类问题就算判错了后果也很轻（顶多多问一句/少问一句），可以继续用现有的双漏斗设计，不需要上结构化约束。真正需要精确的是"喂给法律结论的事实"，不是"要不要接话"。

4. **抽取到的值在同一轮回复里顺带回显确认**，不做成单独的确认页面："好的，记录你们是提供者、系统已上线"——比强制走一个"请核对以下内容"的完整表单页面更自然，又能让用户随口纠正，不需要在硬确认关卡和盲目信任之间二选一。

## 13. 生效日期维度（AI Act 分阶段生效）

AI Act 不是一次性生效，义务清单需要带时间信息，不能只回答"你要做什么"，还要回答"你什么时候必须做完"。

**里程碑**（月份级把握，实现时对照官方文本核实到日）：
- 2025年2月：禁止用途（Art.5）+ AI素养义务生效
- 2025年8月：GPAI模型义务（第五编）、治理机构、罚则条款生效
- 2026年8月：主体条款生效——高风险系统的大部分义务（Art.9-19）、透明度义务（Art.50）
- 2027年8月：受欧盟产品安全法规管辖的产品安全组件类高风险系统（Annex I 情形），适用更晚过渡期

**实现方式**：
1. `law_texts/ai_act_articles.json` 每条目加 `effective_date` 字段
2. 报告生成时用"今天日期 vs effective_date"**动态计算**生效状态（已生效 / 距生效还有X天），不要写死，保证任何时候演示时效性都是对的
3. **`legal_deadline`（法律生效日期，代码算出的客观事实）和 `priority`（P0/P1/P2，业务紧迫度判断）拆成两个独立字段**，不要混在一条判断里；报告排序建议先按 `legal_deadline` 后按 `priority`
4. 过渡期/祖父条款细节先不做，避免范围失控

## 14. 审计留痕（结论可追溯）

现有 `Ledger` 只是调试用的内部日志，建议升级成正式产品能力：

- 每条结论记录：使用的模型/版本、生成时间戳、依据的法条语料版本、完整 prompt（或其哈希/版本号）
- 报告里每条结论附带一个可查询的"生成依据"引用，指向对应 Ledger 记录
- 价值点：如果法律修订、或结论被质疑，能够完整复现"当时是怎么得出这个结论的"——这是把内部日志包装成"结论可追溯"这一明确产品能力，而不只是留个调试痕迹

## 15. 仍然开放、暂不阻塞开工的小项

以下两点讨论过但未深入设计，优先级低，可以在实现过程中顺手解决，不必现在定稿：

- **多轮对话中用户回溯修正之前答案**（比如聊到一半说"其实我们不处理儿童数据"）：需要让已经依赖该要件下结论的枢纽重新失效，目前第11节的状态表结构天然支持"重新计算"，实现时注意触发重算即可，不需要额外新设计
- **权衡型结论的专业责任措辞**（要不要加"这不构成正式法律意见"的声明）：产品定位问题，第4/5节已经用"确定性结论 vs 专业判断需复核"做了区分，是否需要更正式的免责声明可以留到接近上线时再定

测试验证：规则型枢纽（第4/5节标"规则型"的行）本质是纯代码逻辑，可以像普通软件一样写单元测试（构造已知答案的场景断言输出），建议在实现这些枢纽的同时顺手补，不必等整个 Agent 写完才验证。
